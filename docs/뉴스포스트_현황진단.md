# 뉴스포스트 운영 현황 진단서

**진단 기준일:** 2026-08-27
**진단 대상:** 「뉴스포스트 작성 관리 시트」(Google Sheets) 전 탭 + 당근 AI CMS(karrot.evenit.co.kr) 화면 + 비즈프로필 초대 절차
**진단 방법:** 시트 전량(252KB) 파싱 후 실측. 아래 수치는 추정이 아니라 시트에서 계산한 값입니다.

## 0. 결론 먼저

**시스템은 이미 잘 만들어져 있습니다. 멈춰 있는 건 시스템이 아니라 운영입니다.**

기존 시트는 `업체 관리(SoT)` → `뉴스포스트 프로그램` → `보고서/주간보고/대시보드` 구조에,
노란색=입력 / 흰색=자동 규칙, COUNTIFS 기반 주제 사용여부 자동 판정까지 이미 들어가 있습니다.
제가 앞서 제안한 설계의 상당 부분은 **이미 구현돼 있습니다.** 새로 만들 것이 아니라 **고쳐야 할 것**이 있습니다.

실측된 문제는 4개입니다.

| # | 문제 | 실측값 | 성격 |
|---|---|---|---|
| **1** | **날짜가 텍스트로 저장돼 기간 집계가 전부 죽어 있음** | ISO 날짜 0건 / `26.07.18` 형식 440건 | 🔴 **버그** |
| **2** | 대시보드 숫자가 작업 시트에서 나오지 않음 | 작업시트 90건인데 대시보드 "작성완료 148·발행완료 137" | 🔴 **신뢰 불가** |
| **3** | 24일째 발행 정지 | 마지막 발행 26.08.03 → 기준일 26.08.27 | 🔴 **노출 손실 중** |
| **4** | 주제 재고가 사실상 없음 | 콘텐츠 아이디어 **4행** / 진행중 업체 49곳 | 🟠 **생산 병목** |

## 2. 문제 1 — 날짜가 텍스트입니다 (가장 먼저 고칠 것)

### 증상

| 지표 | 현재 | 정상이라면 |
|---|---|---|
| 이번 주 작성 건수 | **0** | 계산돼야 함 |
| 이번 달 작성 건수 | **0** | 계산돼야 함 |
| 마지막 작업일이 채워진 업체 | **48곳 중 1곳** | 작업 있는 15곳 전부 |
| 지연 판정 | 2건 | 실제로는 거의 전부 |

### 원인

시트 전체에서 날짜가 `26.07.18` 형태의 **문자열**로 들어가 있습니다. ISO 날짜(`2026-07-18`)는 **0건**입니다.

사용 가이드에 적힌 핵심 수식은 이렇습니다.

```
마지막/다음 작업일 = MAXIFS / MINIFS
```

`MAXIFS`·`MINIFS`는 **날짜 값**에만 동작합니다. 텍스트에는 빈 값을 돌려줍니다.
그래서 마지막 작업일이 안 채워지고 → 지연 판정이 안 되고 → 이번 주/이번 달 집계가 0이 됩니다.
**대시보드의 절반이 이 한 가지 이유로 죽어 있습니다.**

### 조치

`등록일 / 작성 예정일 / 발행 예정일 / 발행일 / 계약 시작일` 5개 열을 실제 날짜 값으로 일괄 변환합니다.
변환 스크립트를 `scripts/시트_날짜정규화.gs`로 넣어 두었습니다 — 백업 사본을 먼저 만든 뒤 1회 실행하면 됩니다.

이후 입력은 셀 서식을 `날짜`로 고정하고 `yyyy-mm-dd` 표시 형식을 씁니다.

> 이 하나를 고치면 지연 탐지·주간보고·대시보드가 **추가 개발 없이** 되살아납니다. 투입 대비 효과가 가장 큰 작업입니다.

## 3. 문제 2 — 대시보드 숫자를 믿을 수 없습니다

작업 시트는 **90건**이 전부입니다(NP-0001~NP-0090, 결번 없음 — 잘린 게 아닙니다).
그중 작업상태 `발행 완료` 41건, `승인 완료` 5건입니다.

그런데 대시보드는 **작성 완료 148건 / 발행 완료 137건**으로 표시합니다.
90건짜리 원장에서 148건이 나올 수 없습니다.

업체별로도 어긋납니다.

| 업체 | 진행률 시트 발행완료 | 작업 시트 실제 |
|---|---|---|
| 실버이음파트너스 | 18 | 4건 등록 |
| 이레서오릉코다리와쭈꾸미 | 27 | 작업 시트에 없음 |
| 마음이 청소 | 14 (280%) | 작업 시트에 없음 |
| 제로영회기역점 | 12 (120%) | 작업 시트에 없음 |

즉 **일부 업체는 작업 시트를 거치지 않고 발행되고, 실적만 진행률 시트에 수기로 들어가고 있습니다.**
진행률이 120%·280%로 나오는 것이 그 증거입니다.

### 왜 위험한가

- 광고주 중간보고에 들어가는 숫자가 원장과 다릅니다. 광고주가 URL을 요구하면 대지 못합니다(URL 보유 27건).
- 어느 업체가 진짜 밀렸는지 알 수 없어, 46곳 중 어디에 인력을 넣을지 판단이 안 됩니다.

### 조치

**원장은 하나여야 합니다.** 발행된 글은 예외 없이 작업 시트에 1행으로 남기고,
진행률 시트의 완료 수량은 **수기 입력을 금지하고 COUNTIFS 수식으로만** 채웁니다(현재 가이드에 적힌 원래 설계대로).

과거분은 소급 입력이 어렵다면, 진행률 시트에 `이관 전 실적` 열을 따로 두고
`완료 = 이관전 실적 + COUNTIFS(작업시트)`로 분리하십시오. **섞지 말고 나누는 것**이 핵심입니다.

## 4. 문제 3 — 24일째 발행이 멈춰 있습니다

작업 시트의 마지막 발행일은 **26.08.03**입니다. 기준일 26.08.27 기준 **24일 공백**입니다.

당근 소식은 **최근 1주일 내 작성된 글** 중에서 홈피드·동네지도 노출 후보를 고릅니다.
즉 24일 공백은 단순 지연이 아니라 **49개 업체 전부가 노출 후보군에서 빠져 있는 상태**입니다.
그동안 광고주는 비용을 내고 있습니다.

### 정체 구간

| 상태 | 건수 | 비율 |
|---|---|---|
| 보류 | 20 | 22% |
| 수정 중 | 12 | 13% |
| **승인 상태 = 수정 요청** | **28** | **31%** |

**초안 3건 중 1건이 반려**되고 있습니다. 반려는 재작업 시간을 두 배로 만들고, 담당자 의욕을 깎습니다.
반려 사유가 어디에 몰려 있는지(사실 오류인지, 톤인지, 필수기재인지)를 먼저 분류해야 합니다.

### 작업 부하 편중

| 담당자 | 작업 건수 |
|---|---|
| 김사랑 | **40건 (44%)** |
| 장인호 | 2 |
| 허성우 | 1 |
| 담당자3 | 1 |
| **미배정** | **46건 (51%)** |

설정 시트에 등록된 담당자는 14명인데 **실제로 작업이 잡힌 사람은 3명**입니다.
그리고 진행중 49곳 중 **25곳(51%)은 담당자가 아예 없습니다.** 담당자가 없으면 그 업체는 영원히 0%입니다.

## 5. 문제 4 — 주제 재고가 없습니다

`콘텐츠 아이디어` 시트는 **4행**입니다. 그중 1건은 이미 사용완료.
주제를 보유한 업체는 **찰리베이커리·판다팜호매실 2곳뿐**입니다.

진행중 49곳이 매번 백지에서 주제를 고민하고 있다는 뜻입니다.
이것이 "글 쓰는 데 오래 걸린다"의 실제 원인입니다 — 쓰는 게 느린 게 아니라 **뭘 쓸지 정하는 데서 멈춥니다.**

### 조치

업체당 20개씩 콘셉트를 미리 생성해 재고로 쌓습니다(`prompts/콘셉트풀_생성_프롬프트.md`).
진행중 49곳 × 20개 = 980개. AI로 업체당 1회, 한 번에 처리 가능합니다.
`사용 여부`는 이미 COUNTIFS 자동 판정이 걸려 있으므로, 채우기만 하면 그대로 굴러갑니다.

## 6. 마스터 데이터 완성도

`업체 관리`가 Source of Truth인데, 절반이 비어 있습니다.

| 항목 | 채움률 (전체 98행) | 진행중 49곳 기준 미채움 |
|---|---|---|
| 주요 키워드 | 95% | — |
| 보조 키워드 | 93% | — |
| 필수기재 상단/하단 | 81% | 2곳 |
| 목표 수량 | 83% | — |
| URL | 70% | 5곳 |
| **계정** | **48%** | **18곳** |
| **담당자** | **43%** | **25곳** |
| **계약 시작일** | **8%** | 대부분 |
| **업종** | **26%** | 대부분 |

### 이게 만드는 결과

- **계약 시작일 8%** → 기대 진행률·페이스 판정 자체가 불가능. "지연"을 계산할 근거가 없습니다.
- **업종 26%** → 대시보드 업종별 집계가 사실상 무의미(합계 163건인데 분류된 건 일부).
- **계정 미배정 18곳 / 담당자 미배정 25곳** → **이 업체들은 구조적으로 작업이 시작될 수 없습니다.**

진행중 49곳 중 담당자와 계정이 둘 다 있는 곳만 실제 가동 가능합니다.

### 데이터 오염 사례

| ID | 업체명 셀 내용 | 문제 |
|---|---|---|
| C096 | `. 업체명 바다치과의원` | 라벨 텍스트가 값으로 들어감 |
| C098 | `바다치과` | C096과 중복 등록 |
| — | `올가드림뷰티진북점` | 업체명 중복 |

업체명으로 VLOOKUP/COUNTIFS가 도는 구조에서 중복 업체명은 **집계를 조용히 두 배로 만들거나 반으로 나눕니다.**
다행히 `ID`(C001~C099)는 중복이 없습니다 — **집계 키를 업체명에서 ID로 옮기면** 이 문제가 구조적으로 사라집니다.

## 7. 시트와 당근 AI CMS가 갈라져 있습니다

CMS(`karrot.evenit.co.kr`)는 이미 **고객사 관리 · 당근 계정 관리 · AI 초안 생성 · 소식글 검수 · 자동 캠페인 · 데이터**를 갖고 있습니다.
즉 시트가 하려는 일의 상당 부분을 CMS가 이미 하고 있습니다.

그런데 CMS에 등록된 고객사가 시트에서는 비어 있습니다.

| ID | 업체명 | 상태 | 담당자 | 계정 | 목표 |
|---|---|---|---|---|---|
| C090 | 청년도배집수리 | (없음) | (없음) | (없음) | (없음) |
| C098 | 바다치과 | (없음) | (없음) | (없음) | 3 |
| C099 | 달려라용달이사 | (없음) | (없음) | (없음) | (없음) |
| C094 | 좋은환경 | 일시중단 | (없음) | (없음) | 12 |
| C074 | 페토피아 동물메디컬센터 | 일시중단 | 플래닛 | (없음) | 8 |

그리고 **하루두피제주**(초대 수락까지 끝난 비즈프로필)는 시트에 **아예 없습니다**.

**같은 업체 정보를 두 시스템에 각각 넣고 있고, 어느 쪽도 완전하지 않습니다.**
이것이 "업체 정보를 여러 번 입력하지 않게 해달라"는 최초 요구의 실제 형태입니다.

### 역할 분담 권고

| | 당근 AI CMS | Google Sheets |
|---|---|---|
| **역할** | **생산 시스템** | **계약·실적 원장** |
| 담당 | 고객사 프로필, 당근 계정, 키워드, AI 초안, 검수, 자동 배포 | 계약 조건, 목표 수량, 담당자 배정, 진행률, 정산, 광고주 보고 |
| 원본 | 업체 프로필·키워드·계정 | 계약·목표·담당자·실적 |

두 시스템을 잇는 키는 **당근 비즈프로필 ID**입니다. 관리자 홈에 `ID 4067036`처럼 표시되는 값으로,
당근이 직접 발급하므로 상호가 바뀌어도 변하지 않습니다. 마스터에 `당근_비즈프로필_ID` 열을 추가하십시오.
CMS와 시트를 나중에 API나 CSV로 연결할 때 이 값이 유일한 접합점이 됩니다.

## 8. 확정된 사실 (최초 질문 답변 반영)

| 항목 | 확인 결과 | 설계 반영 |
|---|---|---|
| 비즈프로필 초대 절차 | 카톡/문자로 **6자리 초대코드 + 링크** 발송 → 수신자가 `business.daangn.com`에서 코드 입력 → `운영자 수락` → 관리자 홈 진입 | 초대현황 상태값을 실제 절차에 맞춰 확정 (아래 8-1) |
| 소식글 자동 배포 | **당근 AI CMS 보유** (AI 생성 / 자동 캠페인 / 수동 작성 / AI 이미지 / 소식글 검수) | 등록 구간을 "사람이 붙여넣기"에서 **"CMS 자동 배포"**로 변경 |
| 통신판매업 신고 | **전 광고주 미대상** | 하단 필수기재에서 사업자등록번호·대표자명·신고번호 검증 **제외**. 상호·주소·연락처·영업시간만 유지 |
| 업체 관리 시트 | 이미 존재, 구조 양호 | **새로 만들지 않고 고쳐서 씁니다** |

### 8-1. 초대 상태값 (실제 절차 기준)

```
미발송 ──코드 발송──▶ 코드 전달 완료 ──D+3──▶ [리마인드] ──D+7──▶ [코드 재발급]
                            │
                      수신자가 코드 입력
                            ▼
                      운영자 수락 완료 ──▶ 비즈프로필 ID 확보 ──▶ 마스터 등록
```

기록할 값: `초대코드`, `발송일`, `발송수단(카톡/문자)`, `수락일`, `재발급 횟수`, **`당근_비즈프로필_ID`**
초대코드는 재발급 시 값이 바뀌므로(예: `nqe9xz` → `azz8xz`) 마지막 발급분만 유지합니다.

## 9. 우선순위 — 이 순서로 하십시오

| 순위 | 작업 | 소요 | 효과 |
|---|---|---|---|
| **1** | **날짜 텍스트 → 날짜 값 변환** | 30분 (스크립트 1회 실행) | 지연 탐지·주간보고·대시보드 절반이 즉시 되살아남 |
| **2** | **발행 정지 해제** — 가동 가능한 업체부터 재개 | 즉시 | 노출 후보군 복귀. 하루가 곧 손실 |
| **3** | **담당자 25곳·계정 18곳 배정** | 2시간 | 이게 없으면 그 업체는 영원히 0% |
| **4** | **집계 원장 일원화** (진행률 수기 입력 제거, `이관 전 실적` 열 분리) | 3시간 | 보고 숫자를 신뢰 가능하게 |
| **5** | **계약 시작일 채우기** (8% → 100%) | 2시간 | 페이스·지연 판정의 전제 |
| **6** | **콘셉트 풀 생성** (진행중 49곳 × 20개) | 반나절 (AI 일괄) | 생산 병목 해소 |
| **7** | **집계 키를 업체명 → ID로 교체** | 반나절 | 중복 업체명 사고 구조적 제거 |
| **8** | **업종 채우기** (26% → 100%) | 1시간 | 업종별 집계·규제 판정 |
| **9** | 시트 ↔ CMS 역할 분담 확정 + `당근_비즈프로필_ID` 열 추가 | 논의 필요 | 이중 입력 종료 |
| **10** | 반려 사유 분류 → 프롬프트 개선 | 2주 관찰 | 반려율 31% 감축 |

1~3번은 **오늘 할 수 있고, 오늘 해야 하는 일**입니다.
9번은 CMS의 데이터 내보내기/API 지원 여부에 따라 방식이 갈리므로 확인 후 결정합니다.

## 10. 앞서 드린 설계서와의 관계

`docs/뉴스포스트_운영자동화_설계서.md`는 **현행 시트를 보기 전에** 작성한 목표 구조입니다.
확인 결과 그 설계의 상당 부분(업체 마스터 SoT, 입력/자동 열 분리, 주제 사용여부 자동 판정,
진행률·중간보고 자동화)은 **이미 시트에 구현돼 있습니다.**

따라서 그 문서는 **새로 만들 청사진이 아니라, 현행 시트가 도달해야 할 기준선**으로 읽으십시오.
차이가 나는 부분만 정리하면 다음과 같습니다.

| 설계서 항목 | 현행 시트 | 조치 |
|---|---|---|
| 업체 마스터 단일 원본 | ✅ 있음 (`업체 관리`) | 채움률만 올리면 됨 |
| 입력/자동 열 색 분리 | ✅ 있음 (노랑/흰색) | 유지 |
| 주제 사용여부 자동 판정 | ✅ 수식 있음 | 재고를 채워야 작동 |
| 진행률·중간보고 자동화 | ⚠️ 수식은 있으나 날짜 문제로 반쯤 죽음 | 우선순위 1·4번 |
| 집계 키 | ⚠️ 업체명 기준 | 우선순위 7번 (ID로 이전) |
| 계정 관리 탭 | ❌ 마스터에 열 하나뿐 | CMS의 `당근 계정 관리`를 원본으로 사용 |
| 초대 현황 탭 | ❌ 없음 | 신설 (8-1 상태값) |
| 자동 검수(금지어·필수기재) | ❌ 없음 | CMS `소식글 검수`와 중복 여부 확인 후 결정 |
| 발행 공백 7일 경보 | ❌ 없음 | 신설 — 현재 24일 공백을 아무도 자동으로 못 잡고 있음 |
