## 0. 한 장 요약

**진단 한 줄:** 지금 구조의 진짜 문제는 "작업이 많다"가 아니라 **같은 업체 정보를 매 건마다 다시 만난다**는 것입니다.
업체 A의 필수기재·키워드·계정·프로필URL을 월 8건 쓰면 그 업체 정보를 **월 8번 재입력·재확인**하고 있습니다.

**해법 한 줄:** 업체 정보를 **온보딩 1회**에 전부 확정해 `Company Master`에 넣고, 생산 라인은 그 정보를 **참조만** 하게 만듭니다.

### 재설계 후 흐름

```
[L1 온보딩 — 업체당 1회, 사람 40분]
업체 등록(company_id 발번) → 초대 발송 → 계정 배정 → 프로필 SEO·키워드 확정
→ 필수기재 상/하단 확정 → 콘셉트 풀 20개 생성
        │
        ▼
[L2 생산 — 건당, 사람 18분]
콘셉트 자동 픽 → (자동) 업체정보 전량 호출 → AI 제목·본문 초안
→ 자동검수(금지어·필수기재·키워드) → ★사람 검수★ → 상단+본문+하단 자동결합
→ ★당근에 붙여넣기 1회★ → URL 붙여넣기
        │
        ▼
[L3 관리 — 전자동]
진행률·페이스 계산 → 정체/미발행 알림 → 중간보고 초안 자동 생성 → 사람 5분 검토 후 발송
```

★ 표시 2곳만 사람이 합니다. 나머지는 전부 자동입니다.

## 1. 현재 프로세스 재설계

### 1.1 왜 순서를 바꿔야 하는가

현행 14단계는 **시간 순서**로 나열돼 있습니다. 그런데 실제 비용 구조는 **반복 주기**로 갈립니다.

| 반복 주기 | 현행 단계 | 성격 |
|---|---|---|
| 최초 1회 | (없음 — 시트가 그때그때 생김) | 인프라 |
| 업체당 1회 | 2, 3, 5, 6 | 준비 |
| **건당 반복** | **7, 8, 9, 10, 11, 12** | **생산 — 여기가 비용의 85%** |
| 상시/주기 | 1, 4, 13, 14 | 관리 |

문제는 **준비(2·3·5·6)와 생산(7~12)이 섞여 있다**는 점입니다. 필수기재 상/하단은 업체당 1회 확정하면 끝날 일인데, 지금은 건당 복붙 작업으로 내려와 있습니다. 이게 건당 5분 × 160건 = 월 13시간을 잡아먹습니다.

### 1.2 재설계: 4레이어 구조

```
L0. 인프라 (최초 1회)
    └ 시트 7탭 생성 · Apps Script 설치 · 계정 풀 정리

L1. 온보딩 (업체당 1회, 계약 시작 시)          ← 사람 시간을 여기에 몰아넣는다
    ├ ① 업체 등록 → company_id 자동 발번
    ├ ② 초대 발송 → 상태 추적 시작
    ├ ③ Google 계정 배정 → 중복 자동 검사
    ├ ④ 비즈프로필 SEO 진단 → 메인 5 / 롱테일 5 키워드 확정
    ├ ⑤ 필수기재 상단·하단 확정 (통신판매업 대상 여부 판정 포함)
    └ ⑥ 콘셉트 풀 20개 생성 (2~3개월치 소재 선재고)

L2. 생산 (건당 반복)                            ← 여기를 최대한 얇게
    콘셉트 픽 → 정보 자동호출 → AI 초안 → 자동검수 → 사람검수 → 등록 → URL

L3. 관리 (전자동 + 사람 확인)
    진행률 · 페이스 · 정체 알림 · 중간보고
```

**핵심 전환:** L1에 40분을 쓰면 L2에서 건당 54분이 사라집니다. 계약 6개월 × 월 8건 = 48건 기준, 온보딩 40분 투자로 **약 43시간**을 회수합니다.

### 1.3 운영 3원칙 (설계 판단의 기준)

1. **단일 입력 원칙** — 같은 값은 시스템 전체에서 단 한 곳에서만 입력한다.
   시트 열은 **흰색 = 사람이 입력 / 회색 = 자동**으로 색을 고정하고, 회색 열은 시트 보호를 걸어 입력 자체를 막습니다.
2. **파생 금지 원칙** — 계산 가능한 값은 절대 손으로 넣지 않는다.
   (진행률, 완료 수량, 콘셉트 사용여부, 계정 최근사용일, 잔여 콘셉트 수 → 전부 수식)
3. **사람 게이트 최소화** — 사람은 *판단*만, *이동·복사·집계*는 기계.
   최종적으로 사람 게이트는 **② 사람 검수**와 **⑪ 당근 등록** 딱 2개만 남깁니다.

## 3. 데이터 아키텍처 — company_id 중심 설계

### 3.1 왜 회사명 문자열로 연결하면 안 되는가

회사명을 키로 쓰면 아래에서 반드시 깨집니다.

- `(주)행복치과` / `행복치과` / `행복 치과` — 표기 흔들림 → VLOOKUP `#N/A`
- 지점 확장: `행복치과` → `행복치과 신촌점`, `행복치과 목동점` — 과거 데이터가 어디 붙는지 불명
- 상호 변경: 리브랜딩 한 번에 **과거 발행 실적 전체가 고아 데이터**가 됨
- 동명 업체: 다른 지역 동일 상호 → 데이터 오염 (가장 위험 — 조용히 잘못 붙음)

`company_id`는 **한 번 발번하면 절대 바뀌지 않는 값**이고, 업체명은 그저 `company_id`에 딸린 표시용 속성이 됩니다.

### 3.2 구조도

```
                        ┌───────────────────────────┐
                        │   01_Company_Master       │
                        │   PK: company_id (CM-001) │  ← 업체 정보의 유일한 원본
                        └────────────┬──────────────┘
                                     │ company_id
        ┌───────────────┬────────────┼────────────┬──────────────┐
        ▼               ▼            ▼            ▼              ▼
 ┌────────────┐  ┌────────────┐ ┌──────────┐ ┌──────────┐ ┌───────────┐
 │02_계정관리 │  │03_초대현황 │ │04_콘셉트 │ │05_작성   │ │07_보고로그│
 │account_id  │  │invite_id   │ │concept_id│ │post_id   │ │report_id  │
 └────────────┘  └────────────┘ └────┬─────┘ └────┬─────┘ └─────┬─────┘
                                     │            │             │
                                     └──사용여부◄─┘             │
                                                  │             │
                                     ┌────────────▼─────────────▼──┐
                                     │        06_대시보드          │
                                     │  (전부 수식 — 입력 셀 없음) │
                                     └─────────────────────────────┘
```

읽는 법: **화살표 방향으로만 데이터가 흐릅니다.** 05(작성)는 01·02·04를 *읽기만* 하고, 04의 "사용여부"는 05를 *역참조*해서 자동 계산됩니다. 어디서도 같은 값을 두 번 입력하지 않습니다.

### 3.3 company_id 운영 규칙

| 규칙 | 내용 |
|---|---|
| 형식 | `CM-001` (접두 CM + 3자리 일련번호) |
| 발번 | 업체명 입력 시 Apps Script가 자동 채번 — 사람이 정하지 않음 |
| 불변성 | 상호 변경·업종 변경·재계약에도 **절대 변경/재사용 금지** |
| 종료 업체 | 행을 지우지 않고 `상태 = 종료`로만 변경 (과거 실적 보존) |
| 재계약 | 같은 `company_id` 유지, `계약시작일/종료일`만 갱신 |
| 선택 UI | 사람은 항상 **업체명 드롭다운**으로 고르고, `company_id`는 자동 변환 |

> 사람은 `company_id`를 외울 필요가 없습니다. 사람은 업체명을 고르고, 시스템은 id로 연결합니다.

## 4. 광고주/업체 초대 자동화

### 현재 문제점

- 초대했는지 여부가 **담당자 기억과 카톡 스크롤**에 남아 있음
- 광고주가 수락을 안 하면 방치 → 계약 시작일은 지났는데 발행은 0건
- 재초대 시점 판단 기준이 없음

### 상태머신 설계

```
미초대 ──발송──▶ 초대완료 ──(D+0)──▶ 수락대기 ──수락──▶ 등록완료
                     │                    │
                     │              D+3 경과 → [자동 리마인드]
                     │                    │
                     │              D+7 경과 → [재초대 필요 · 적색]
                     ▼                    ▼
                  발송실패 ◄──────────  만료/거절 ──▶ 재초대(횟수+1)
```

### 자동화 방식

| 항목 | 구현 |
|---|---|
| 상태 기록 | `03_초대현황` 탭 — company_id 기준 1행 |
| 경과일 | `=TODAY()-초대발송일` 자동 계산 |
| 알림 필요 | `상태="수락대기" AND 경과일>=3` → `알림필요=Y` (수식) |
| 자동 리마인드 | Apps Script 시간 트리거(매일 09:30) → `알림필요=Y` 목록을 담당자에게 메일/슬랙 1통으로 발송 |
| 대시보드 노출 | `06_대시보드`에 업체별 초대상태 컬럼 자동 표시 |
| 재초대 문안 | 템플릿 + 업체명·담당자명 자동 치환 |

**주의:** 당근 비즈프로필의 실제 멤버 초대 화면·수락 절차는 플랫폼 UI 기준으로 한 번 확인이 필요합니다(14장 확인목록). 위 상태머신은 어떤 초대 방식이든 그대로 적용되도록 플랫폼 중립적으로 설계했습니다.

### 절감

초대 상태 확인·재초대 누락 대응에 쓰던 **월 약 120분 → 0분** (알림을 받아 실행하는 시간만 남음).

## 5. Google 계정 관리

### 설계 원칙 — 인증정보는 시트에 두지 않습니다

**절대 하지 말 것:** 일반 Google Sheet에 비밀번호·복구코드·2FA 시드를 평문으로 저장.

| 대상 | 저장 위치 |

추가 통제: 해당 시트는 **운영 담당자 그룹에게만 공유**, 링크 공유 OFF, 다운로드/복사/인쇄 제한, 편집 기록 주기 점검.

| account_id | 구글계정 | 배정_company_id | 배정업체명 | 상태 | 최근사용일 | 2FA | 인증정보_보관위치 | 중복배정경고 | 비고 |
|---|---|---|---|---|---|---|---|---|---|
| AC-001 | ops01@… | CM-001 | 행복치과 | 사용중 | (자동) | Y | vault/… | (자동) | |

`상태` 값: `미배정 / 사용중 / 잠김 / 회수예정 / 회수완료`

## 6. 뉴스포스트 작성 시트 자동화 (핵심)

### 설계: 1행 = 뉴스포스트 1건 (기획부터 발행까지 한 행에서 끝)

기존처럼 기획시트·작성시트·발행시트를 나누면 행이 시트 사이를 이동해야 하고, 이동할 때마다 복사와 누락이 생깁니다.
**한 행이 상태값만 바꾸며 끝까지 갑니다.**

```
상태 전이:  기획 → 초안 → 검수대기 → (수정요청) → 승인 → 등록완료
```

### 업체 선택 → 자동 호출되는 항목 (사람은 절대 입력하지 않음)

`B열 업체명` 드롭다운 하나만 고르면:

| 자동 호출 열 | 출처 |
|---|---|
| company_id | 01 Master |
| 업종 / 지역(시군구·동) | 01 Master |
| 비즈프로필 URL | 01 Master |
| 배정 Google 계정 | 02 계정관리 |
| 메인 키워드 5 / 롱테일 키워드 5 | 01 Master |
| 금지 키워드 | 01 Master |
| 필수기재 상단 | 01 Master |
| 필수기재 하단 | 01 Master |
| 톤앤매너 | 01 Master |
| 통신판매업 대상 Y/N | 01 Master |
| **최근 발행 주제 3건** | 05 자체 역참조 (중복 회피용) |
| 잔여 콘셉트 수 | 04 콘셉트DB |

구현은 단순합니다. 각 열에:

```
=IFERROR(XLOOKUP($C2, '01_Company_Master'!$A:$A, '01_Company_Master'!D:D), "")
```

(`$C2` = 자동 변환된 company_id, `D:D` = 가져올 열)

**중요:** 이 열들은 전부 **시트 보호**를 걸어 사람이 덮어쓰지 못하게 합니다. 덮어쓰기가 가능하면 "Master는 바뀌었는데 작성시트는 옛날 값"인 상태가 조용히 생깁니다 — 필수기재 하단에서 이게 발생하면 법적 리스크가 됩니다.

### 절감

건당 업체정보 입력·확인 8분 → 0분. **월 약 1,280분(21시간).**

## 7. 필수기재 상단/하단 자동 관리

### 현재 문제점

- 매 건 복붙 → 건당 5분
- 더 큰 문제는 시간이 아니라 **버전 드리프트**: 광고주가 전화번호·주소를 바꿨는데, 담당자가 예전 게시물을 복사해 쓰면 **틀린 정보가 계속 재생산**됩니다. 통신판매업 대상 업체라면 표시의무 위반 소지가 있습니다.

### 설계

`01_Company_Master`에 두 개의 긴 텍스트 열로 보관하고, **원본은 여기 한 곳뿐**입니다.

**필수기재 상단** (본문 시작부):
- 업체명(브랜드명) 1회 이상
- 메인 키워드 `[동네]+[업종]` 1회 이상 — 동네지도 검색 노출용

**필수기재 하단** (CTA/부가정보):
- 상호 · 영업소 주소 · 연락처 · 영업시간 (전 업체 공통, 신뢰도·전환 목적)
- ~~통신판매업 신고 대상인 경우 대표자 성명 · 사업자등록번호 · 신고번호 추가~~
  → **확인 결과 현재 전 광고주가 통신판매업 신고 미대상입니다.** 따라서 이 검증은 적용하지 않습니다.
  → 다만 Master의 `통신판매업_대상` 열(기본값 N)은 남겨 두십시오. 온라인 결제·판매를 시작하는 광고주가
    생기면 그때 Y로 바꾸는 것만으로 검증이 켜지도록 설계돼 있습니다.

### 결합 흐름 (사람 개입 0)

```
업체 선택 ──▶ 상단 자동 로드 ──▶ AI 본문 생성 ──▶ 하단 자동 로드
                                                      │
                                                      ▼
                                   [최종_게시본문] = 상단 + 개행 + 본문확정 + 개행 + 하단
                                                      │
                                        (한 셀 클릭 → 복사 → 당근에 붙여넣기)
```

`최종_게시본문` 열은 수식 또는 Apps Script로 결합되며 **사람이 편집할 수 없는 회색 열**입니다.

### 안전장치

- `자동검수`가 최종본문에 상단 요소(업체명·메인키워드)와 하단 요소(상호·연락처, 대상이면 사업자등록번호)가 실제로 들어있는지 **문자열 검증**
- 하나라도 없으면 `상태`를 `승인`으로 바꿀 수 없게 차단 (Apps Script `onEdit` 검증)
- Master의 필수기재를 수정하면, **아직 미발행 상태(기획/초안/검수대기)인 행에는 자동 반영**되고, 이미 등록완료된 행은 발행 당시 값이 남습니다 (이력 보존)

### 절감

건당 5분 → 0분. **월 약 800분(13시간)** + 오기재 리스크 제거.

## 8. 뉴스포스트 콘셉트 DB

### 현재 문제점

매 건마다 "이 업체 뭐 쓰지"를 백지에서 고민하고, AI에게 업체 설명을 처음부터 다시 합니다. 게다가 **지난달에 쓴 주제인지 기억으로 확인**합니다.

### 설계: 소재는 미리 만들어 재고로 쌓아둔다

당근 소식은 **반응 좋은 소재가 3가지로 정해져 있습니다 — 상품·서비스 소개 / 노하우 공유 / 매장 일상.**
그래서 콘셉트DB는 이 3개를 상위 카테고리로 고정하고, 그 아래에 실무 유형을 답니다.

```
업체 A (CM-001)
├─ [상품·서비스 소개]  ├─ 서비스 설명형
│                      ├─ 이벤트형
│                      └─ 가격/패키지형
├─ [노하우 공유]       ├─ 고객 고민형
│                      ├─ FAQ형
│                      └─ 체크리스트형
└─ [매장 일상]         ├─ 사례형
                       └─ 지역 키워드형
```

### 탭 구조 (`04_콘셉트DB`)

| 열 | 설명 | 입력/자동 |
|---|---|---|
| concept_id | CP-0001 | 자동 |
| company_id | 소속 업체 | 자동(업체명 선택) |
| 콘텐츠_카테고리 | 상품·서비스 / 노하우 / 일상 | 입력(드롭다운) |
| 세부유형 | 고객고민형·FAQ·사례형·지역키워드형·이벤트형·서비스설명형 | 입력 |
| 콘셉트_한줄 | "인수 전 확인할 3가지" 같은 한 줄 | AI 생성 |
| 핵심키워드 | 이 건에서 쓸 키워드 1~2개 | AI 생성 |
| 고객_고민 | 이 소재가 해결하는 고민 | AI 생성 |
| 차별점_연결 | 어떤 강점으로 연결할지 | AI 생성 |
| 우선순위 | 1~5 | 사람 조정 |
| **사용여부** | 미사용/사용됨 | **자동** `=IF(COUNTIF(05!concept_id, A2)>0,"사용됨","미사용")` |
| 사용_post_id / 사용일 | 어느 건에 쓰였는지 | 자동 |

> `사용여부`를 사람이 체크하게 만들면 반드시 틀어집니다. **05 작성시트를 역참조해 자동 계산**하는 것이 이 설계의 핵심입니다.

### 운영 루프

## 9. 제목·본문 초안 자동 생성

## 11. 등록 · 발행 URL 기록

### 등록 — ⚠️ 전제 변경됨

**최초 작성 시점의 판단:** 공개 게시 API가 확인되지 않으므로 사람이 붙여넣는다.

**확인 후:** 이미 **당근 AI CMS**(`karrot.evenit.co.kr`)를 보유하고 있고, `자동 캠페인` 기능이 있습니다.
따라서 이 구간은 **CMS 자동 배포로 대체 가능**합니다. 아래 수동 절차는 CMS를 쓰지 않는 업체의 대비책으로만 남깁니다.

> 다만 원칙은 유지합니다. **직접 만든 스크립트로 당근 계정에 자동 로그인해 게시하는 것은 하지 않습니다.**
> CMS는 별도 제공 서비스이므로 그 서비스의 배포 방식과 약관 적합성은 공급사에 확인하십시오.

CMS를 쓰지 않는 경우, 사람이 하는 일을 **최소 동작**으로 줄입니다.

1. `최종_게시본문` 셀 클릭 → 복사 (상단+본문+하단이 이미 결합된 완성본)
2. 당근에 붙여넣기 + 사진 첨부
3. 발행 후 URL 복사 → 시트 `발행URL` 열에 붙여넣기

### URL 입력 1회 → 자동 전파

`발행URL`을 붙여넣는 순간 Apps Script가:

- `상태` → `등록완료`
- `발행일` → 오늘 날짜 자동 기록
- 해당 `concept_id` → 콘셉트DB에서 `사용됨`으로 자동 전환
- 계정관리 `최근사용일` 갱신
- 대시보드 진행률·페이스 재계산
- 보고용 발행 목록에 자동 편입

즉, **사람이 값을 옮겨 적는 곳은 이 URL 한 칸이 마지막입니다.**

### 절감

등록 6분 → 4분, URL 기록 2분 → 1분. **월 약 480분(8시간).**

## 12. 진행률 관리 · 광고주 중간보고

### 12.1 진행률 — 수기 집계를 전부 없앱니다

`06_대시보드`는 **입력 셀이 하나도 없는 탭**입니다. 전부 수식입니다.

| 지표 | 계산식(개념) | 용도 |
|---|---|---|
| 완료 건수 | `COUNTIFS(05!company_id, id, 05!상태, "등록완료")` | 실적 |
| 진행률 | `완료 / 목표_뉴스포스트_수` | 계약 이행률 |
| **기대 진행률** | `(TODAY()-계약시작일) / (계약종료일-계약시작일)` | 페이스 기준선 |
| **페이스 판정** | `진행률 - 기대진행률` → −10%p 미만이면 `지연` | **선제 대응 신호** |
| 마지막 발행 경과일 | `TODAY()-MAX(발행일)` | 노출 리스크 |
| 콘텐츠 공백 경보 | 경과일 **7일 초과 → 적색** | 아래 설명 |
| 검수 대기 건수 | 상태별 COUNTIFS | 병목 탐지 |
| 정체 건수 | 최종수정일 D+3 초과 & 미완료 | 병목 탐지 |
| 잔여 콘셉트 | `COUNTIFS(04!company_id, id, 04!사용여부,"미사용")` | 소재 재고 |
| 초대/계정 상태 | 02·03 참조 | 온보딩 누락 탐지 |

> **7일 경보의 근거:** 당근 소식은 *최근 1주일 내 작성된 소식* 중에서 이웃 관심도가 높은 것을 골라 홈피드·동네지도에 무료 노출합니다.
> 즉 **1주일 넘게 안 올리면 노출 후보군 자체에서 빠집니다.** 진행률이 100%여도 발행이 몰려 있으면 노출 성과는 나쁩니다.
> 그래서 대시보드는 "몇 건 했나"뿐 아니라 **"공백이 생겼나"**를 같은 비중으로 봅니다. 이건 단순 관리지표가 아니라 성과지표입니다.

### 12.2 중간보고 자동 생성

**현재:** 업체당 30분 × 20곳 = 월 10시간. 대부분이 URL 모으고 표 만드는 시간입니다.

**설계:** 트리거(월 1회 또는 격주) → 기간 내 발행 데이터 자동 집계 → 템플릿 채움 → Google Docs 또는 메일 초안 생성 → **사람이 5분 검토·코멘트 추가 후 발송**.

자동 채워지는 항목:
- 보고 기간 / 목표 대비 발행 건수 / 누적 진행률
- 발행 목록 (제목 + 콘셉트 유형 + 발행일 + URL)
- 다룬 소재 분포 (상품소개 n건 / 노하우 n건 / 일상 n건)
- 사용한 메인·롱테일 키워드
- 다음 기간 예정 콘셉트 3개 (콘셉트DB 우선순위 상위 미사용분)

사람이 추가하는 항목: **성과 해석 · 광고주 제안 · 협의 사항** (A 영역)

템플릿: `templates/중간보고_템플릿.md`

### 절감

진행률 집계 월 240분 → 0분, 중간보고 월 600분 → 100분. **합계 월 740분(12시간).**
